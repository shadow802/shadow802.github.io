Harness开发流程

发表于 2026-08-03 分类于 AI

前言

​ 模型能力突飞猛进，Claude Code大量删除系统提示词适配新模型能力，通过消融实验来观察每段提示词对新模型的影响。并声称已经无法在新模型上复现提示词注入的攻击。

​ Boris Cherny: We Cut 80% of Claude Code’s Prompt

​ 围绕大模型开发，涌现了大量的新名词：Prompt Engineering → Context Engineering → Harness Engineering、本体论等。对于这些概念，如果仅停留在字面定义和理论层面，往往晦涩难懂，甚至容易陷入”概念理解了，但不知道如何落地”的困境。真正理解这些概念，需要将其放回实际的开发过程中，通过具体的工程实践寻找与之对应的具象化实体：一个 Prompt、一段 Context、一套 Harness、一组 Tool，甚至是一套完整的 Agent Runtime。只有当抽象概念与具体的工程实践建立起对应关系，才能真正理解这些概念背后的设计思想，以及它们试图解决的实际问题。

流程

​ 基于实际工作的需要：

  • 分析了OpenCode以及使用OpenCode开发的一个SRE智能体。

  • 设计并编写了K8s容器平台上关于网关的Skill。

​ 关于智能体Harness开发，主要从四个方面来说：

需求

结构化数据

​ 在明确了业务场景和目标后，应该以标准结构化的数据结构，来描述智能体的输入和输出，可以采用YAML、JSON、XML、Markdown文档等形式；结构化的数据，有利于智能体快速理解意图和目标，不容易产生歧义。这里称之为契约，也就是schema。

评测集

​ 同时根据已有的场景和目标，可以很容易构建出评测的数据集，其中最主要的是：

  1. 正向测试：确保智能体能准确实现业务目标，提升准确率。
  2. 工具调用：判断工具是否正常被调用，并符合调用结果预期。
  3. 历史缺陷：不断被补充的测试集，保证已经出现的问题，在后续版本迭代中不会再次出现。

设计

​ 智能体设计，关系到智能体最后业务目标的达成效果。

架构

​ 从架构上，目前主流实现有两种：

  • Agent：无固定流程，需要借助模型的规划能力或者不断执行、观察寻找合适的实现的场景。
  • Workflow：适合有明确步骤、流程、前后依赖的场景。例如LangGraph的DAG。

​ Agent又分为单Agent和多Agent。

​ 多Agent实现方案中，往往有一个Agent负责规划、分配、协调整体流程。有通过A2A做Agent通信的，这样每个Agent都单独负责一个专业领域，提供能力供其他Agent使用。也有主Agent单独启用SubAgent负责某个具体的事情，完成后自动销毁的。多Agent架构优点在于各司其职，能在复杂的场景中分工明确（不污染上下文），并发执行（提高效率），最终得到理想的结果。缺点在于A2A通信机制复杂，架构繁重。

​ 单Agent的实现，有提供SDK重度依赖编码的，例如Pi和LangGraph；也有一些轻量级开源框架，例如OpenCode，只需要编写配置和Markdown文档，即可轻松实现。

本体论

​ 每个智能体，都有自己的世界观，它认识世界的方式，是开发者定义的。在垂直领域，智能体所负责的模块中，应当以简练的语言，清晰的表述：图表、架构图、流程图、结构化文本等，向Agent传递它所需要的领域宏观知识，以让它对所负责的领域中的专业术语、实体关系、工作流程、工作边界有清晰的认识。给它塑造人格和灵魂。也就是我们常说要做什么事情的业务知识。

约束

​ 这属于安全的范畴，对于权限、边界做一个整体的陈述。明令禁止的。

模型

​ 模型，是智能体的大脑，既要智力够用，又要考虑安全、成本等一些问题，需要物美价廉，而不是杀鸡用牛刀（浪费token）或者小马拉大车（再牛的Harness也只能治标不治本）。

​ 常见的比如编码能力，公认的Claude Code，国内可替代的GLM 5.2、Kimi k3。综合能力ChatGPT，国内的DeepSeek（量大管饱）。还有一些专门用来做视觉、图片、视频生成的模型。可通过arena leaderboard做初步筛选，并结合自身业务场景试用选择。

能力

​ 好的模型，使智能体拥有了聪明的大脑；合适的架构，使智能体拥有了完美的骨架。而扩展出来的能力，则使智能体拥有了五官、手脚，可以获取更多的信息，做更多专业的事情。

​ MCP、Skill本质上都是复用的哲学，为了将数据、工具封装成统一的能力，在多个智能体共同使用，达到一次封装，到处复用的目的，Plugins只不过将MCP、Skill打包在了一起，方便分发。

​ 在低代码的开发框架中，可以在智能体执行的整个生命周期中打桩，进行一些个性化的灵活的自定义操作。例如监听某个事件，在智能体循环开始或者结束时做一些操作。

​ 链路和日志，为智能体执行历史提供了审计的能力，在安全的大背景下，这个能力尤为重要。

​ 像OpenCode这种高代码智能体框架，内置了许多Slash命令，并支持扩展自定义Slash命令，这在TUI上应用广泛。

安全

​ 安全，是一个非常重要的功能，需要合理设置权限，明确智能体的处理边界，避免因幻觉或者是不可控的因素导致的安全事故。安全的约束，遍布于智能体的系统提示词（有些以MarkDown文件保存）、Skill的能力约束、隔离的级别；必要时，需及时引入人工二次确认和授权。

记忆

​ 记忆的管理，目前低代码编程框架和高代码开源框架均有默认处理，在必要情况下，开发者也可以自行扩展。记忆目前常见于存放文件、SQLite数据库等，高阶的有向量数据库、图数据库、知识图谱等。

上线

​ 智能体最终是要开放自己，为用户提供服务。

服务方式

​ 目前主流的服务方式：

  • 编码集成：SDK、A2A
  • 图形化：UI
  • 命令行：TUI、CLI

部署方式

​ 根据安全级别，有单独启动安全沙箱，严格控制其网络权限、密钥获取及本地数据权限的。也有直接部署容器内，在同一个容器内，按会话、智能体级别进行数据隔离的。

回归

​ 回归是一个长期的过程，需要日拱一卒的坚持积累评测集，并配合上自动化回归测试来提高执行的频次和效率。害怕变更，更应该时时变更；害怕集成，更应该时时集成，坚持正确的事，将其做成一种习惯，才能克服困难，保持先进。

监控

​ 智能体上线后，需监控其异常情况、正确率，以纠正其行为。如果模型发生变更、或者业务场景、目标发生变化，要及时调整实现。

评测

​ 不论是新需求的迭代，还是模型变化，架构升级，都应当反向维护测试集，使测试集能覆盖更多情况，更符合业务的目标，自动反复执行，以确认新迭代的智能体的表现，不至大规模偏离原有目标。

优化

​ 新的模型，意味着更强的大脑；新的Harness架构，也可能代表着更高的准确率。没有一劳永逸的事情，都需要随着需求和技术不断推陈出新，顺应时代，贴合业务需求和目标，不断迭代自己。

前言

随着模型能力持续提升，曾经有效的提示词和工具设计也需要被定期重新评估。Claude Code 团队通过消融实验判断既有指令是否仍有必要，并显著精简系统提示词，以减少冗余约束对新模型能力的影响。
围绕大模型应用开发，业界的关注范围正在从 Prompt Engineering 扩展到 Context Engineering 和 Harness Engineering。Prompt Engineering 关注指令设计，Context Engineering 关注上下文的选择、组织和更新，Harness Engineering 则关注模型外围运行系统的设计。本体论属于领域知识建模方法，可以作为上下文和知识系统的一部分。
参考：Boris Cherny: We Cut 80% of Claude Code’s Prompt

流程

基于实际工作需要，我分析了 OpenCode 及一个基于 OpenCode 开发的 SRE Agent，并设计、编写了面向 Kubernetes 容器平台网关场景的 Agent Skill，由此总结出以下 Harness 开发流程：

本文所称 Harness，是围绕模型构建的一组运行机制，包括提示词与上下文管理、Agent 循环、工具调用、权限控制、状态与记忆、评测、可观测性以及人工审批等。其开发过程可以归纳为目标与契约、Harness 设计、上线运行和持续回归四个阶段。

一、目标与契约

1. 输入输出契约

明确业务场景和目标后，应为工具接口、系统集成边界及关键输出定义可验证的契约。JSON、YAML 和 XML 可以作为数据序列化格式，Markdown 适合承载说明性或半结构化内容；JSON Schema、OpenAPI、Protocol Buffers 或代码类型定义可以进一步描述字段、类型、约束和错误结构。
一份完整的契约还应明确必填字段、取值范围、错误处理、版本兼容、幂等性和敏感字段处理规则。面向用户的开放意图可以继续使用自然语言表达，在工具调用和系统交互阶段再转换为结构化数据。

2. 评测集与指标

评测集应覆盖正常任务、边界与异常输入、工具失败、多轮状态、安全攻击和历史缺陷。工具评测需要检查调用时机、工具选择、参数、顺序、重试策略及副作用是否符合预期。
评价指标应与任务类型匹配。除答案准确率外，还可以使用任务完成率、约束满足率、工具调用正确率、人工评分、延迟和成本。复杂任务的标准答案和评分规则通常需要领域专家参与制定。

二、Harness 设计

1. 架构

Agent 系统位于确定性工作流与模型自主决策之间的连续谱上。确定性工作流由代码预先定义步骤、分支和依赖；Agent 式执行由模型动态决定任务分解、工具选择和下一步动作；混合架构则使用工作流约束关键步骤，将局部复杂任务交给 Agent 决策。
LangGraph 使用状态图描述节点和状态转换，支持顺序执行、条件分支、循环和并行。单 Agent 与多 Agent 描述协作单元的数量，通用 Agent 与垂直领域 Agent 描述职责范围，这两个维度可以自由组合。
多 Agent 可以采用 Supervisor/Worker、路由、Handoff、并行专家或评审—执行等模式。A2A 适合跨进程、跨服务或跨组织的 Agent 互操作，同一运行时中的 SubAgent 通常由框架直接调度。多 Agent 能够隔离专业上下文、并行处理独立任务，同时也需要处理通信成本、延迟、状态一致性和错误传播等问题。
Agent 的实现方式还可以按抽象层次区分：LangGraph 等编排框架通过代码定义状态、节点和执行流程；OpenCode 等可配置编码 Agent 则内置 Agent 循环、工具和交互界面，并通过配置、Markdown、插件和外部工具进行扩展。

2. 本体论与约束

本体论是对领域概念、实体、属性、关系和规则的显式建模。例如在 Kubernetes 领域，可以定义 Cluster、Namespace、Workload、Pod 和 Service 等实体，以及“属于”“选择”“暴露”“调度到”等关系。本体论可以通过术语表、Schema、知识图谱或结构化文档表达，为 Agent 提供一致的领域语义。
Agent 的约束包括业务规则、输出契约、资源预算、权限边界和合规要求。提示词负责向模型说明行为规范，权限系统、工具参数校验、沙箱和审批机制负责执行关键约束。

3. 模型

模型选型应明确到具体模型和版本，并结合自身评测集，从任务能力、工具调用、上下文长度、延迟、Token 价格、吞吐量、部署方式、数据合规和稳定性等方面综合比较。
通用排行榜可以用于缩小候选范围，最终选择仍应由业务评测结果决定。还可以通过模型路由，让不同难度和风险等级的任务使用不同模型，在效果、成本和响应速度之间取得平衡。

4. 能力扩展

MCP 和 Agent Skill 都有助于能力复用，但承担不同职责。MCP 是连接 Agent 与外部工具、资源和提示模板的通信协议；Skill 是由指令、脚本和参考资源组成、可按需加载的能力包。Plugin 是特定平台定义的扩展与分发单元，可以包含代码、命令、Hook、Agent、Skill 或 MCP 配置。
部分平台提供生命周期 Hook，可在会话开始、工具调用前后或任务结束时执行校验、审批、日志记录等逻辑。Trace 和日志为问题定位与审计提供基础数据；正式审计还需要记录身份、授权决策和关键状态变更，并满足防篡改、脱敏、访问控制及留存要求。

5. 安全

Agent 安全应采用纵深防御。系统提示词和 Skill 用于描述行为规范，生产环境则通过工具最小权限、默认拒绝、文件与网络沙箱、密钥隔离、参数及输出校验、外部内容不可信处理、高风险操作审批、租户隔离、调用审计、资源限额和紧急停止机制建立安全边界。

6. 状态与记忆

Agent 的记忆可以分为当前上下文、会话状态和跨会话长期记忆。不同框架对此提供的能力不同，有些保存消息或 Checkpoint，有些提供持久化和长期记忆接口。完整的记忆系统还需要设计写入、检索、更新、遗忘及隐私策略。
文件、关系数据库、键值数据库、向量数据库和图数据库分别适合静态知识、结构化状态、快速查询、语义检索和关系遍历，应根据数据结构、一致性、查询模式、规模和合规要求选择。

三、上线运行

Agent 可以通过 SDK、HTTP/gRPC API、A2A、Webhook 或消息队列与其他系统集成，也可以通过 Web/桌面 UI、TUI、CLI、IDE 插件或自动化任务面向用户和流程提供服务。
部署隔离级别应与任务风险匹配。只读、低风险任务可以采用进程内逻辑隔离；能够执行命令、修改文件或访问网络的 Agent，应优先使用独立进程、容器或微型虚拟机等沙箱。多租户场景还应隔离工作目录、凭证、网络策略、缓存和持久化数据。

四、监控、评测与回归

线上监控应同时覆盖系统指标、模型指标、工具指标、业务指标和安全指标，例如延迟、错误率、Token 成本、工具调用成功率、任务完成率、人工接管率和越权拦截情况。质量指标可以结合抽样标注、用户反馈和延迟获得的业务结果进行估算。
业务目标变化时，应版本化更新评测集和评分标准；模型、提示词或架构变化时，应在固定回归集和独立留出集上比较新旧版本。线上缺陷可以沉淀为回归样例，并持续补充新的留出样例。对存在随机性的任务，可以多次运行并比较均值、分位数和失败率。
新模型和新 Harness 都是候选改进，应通过离线评测、线上灰度实验以及成本、延迟和安全指标综合判断升级效果。版本控制、自动评测、发布门禁、灰度发布和快速回滚机制可以帮助系统以小批量、可验证的方式持续演进。
